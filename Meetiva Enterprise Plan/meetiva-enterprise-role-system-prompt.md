# Meetiva — Enterprise Role & Access Control System

## Context
Meetiva is a meeting-summarization SaaS. The frontend, backend, and admin panel already exist and work. We now need to add a **role-based access control (RBAC) system**, starting with the **Enterprise package** only (Free and Teams packages will come later — build the role system so it's extensible to them, but don't implement their logic yet).

## Roles & Hierarchy

There are 5 roles total. **Super Admin** sits above everything and is internal to us (Meetiva's own team) — it is not part of any customer's organization. Below that, there are 4 roles inside each Enterprise organization, in a strict top-down chain:

```
Super Admin (us, platform-wide)
        │
Admin → Manager → Team Leader → Member    (all scoped to one Organization)
```

**Provisioning rule:** each org-level role can only create/invite the role directly below it. A role cannot skip a level (e.g. Admin cannot directly create Team Leaders or Members — only Managers). Credentials for every role below Admin are generated by our system and handed down manually (copy/share, not auto-email — see "Credential Provisioning" below) by the role above; none of these roles self-register.

### 0. Super Admin (internal, platform-wide)
- Not tied to any single Organization. This is Meetiva's own internal role for our team.
- Logs into the **same Admin Panel**, but with a platform-wide view: can see **every Organization** created on Meetiva and **every user** across the whole platform, regardless of which Enterprise Admin created them.
- Used for our own oversight/support — not part of the customer-facing role chain, and not something a customer Admin can ever obtain or grant.
- One person could plausibly own multiple Organizations as a regular Admin (separate scenario, unrelated to Super Admin) — keep `Organization.admin_user_id` capable of pointing to a user who owns more than one org if that comes up later, but don't build multi-org-per-admin logic now.

### 1. Admin
- Created automatically when a user signs up/logs in on the Meetiva website, selects the **Enterprise** package, and completes payment.
- Owns one Enterprise organization ("tenant"). Cannot see or access any other organization's data.
- Has full access to the **Admin Panel** for their own organization only.
- Can see **all** projects/teams within their organization.
- Creates Manager accounts (sets who is a Manager) and generates their login credentials, then shares them manually (e.g. via email) — Managers do not self-register.
- Assigns Managers to specific projects.

### 2. Manager
- Credentials created by Admin.
- Has access to **both** the Admin Panel (scoped) and the main Meetiva website.
- Can only see/manage the **projects and teams they've been explicitly assigned to** — not the whole org, unlike Admin. A Manager can be assigned to **multiple projects** at once (this is expected/normal, not an edge case).
- Creates Teams for their assigned project(s) — can be done from either the Admin Panel or the website.
- Assigns Team Leaders to the teams they created — **only from the website, not the Admin Panel**.
- Creates Team Leader accounts (generates their login credentials) and shares them manually — Team Leaders do not self-register.

### 3. Team Leader
- Credentials created by Manager.
- Has access to the **Meetiva website only** — no Admin Panel access at all.
- Can only see/manage the team(s) they've been made leader of. A Team Leader **can lead more than one team** (many-to-many, same pattern as Manager↔Project) — this costs no extra seats since it's the same person, so orgs can use their 20-seat cap efficiently instead of being forced into one-leader-per-team.
- Invites Members into their team(s) via the website.
- Creates Member accounts (generates their login credentials) and shares them manually — Members do not self-register.

### 4. Member
- Credentials created by Team Leader.
- Has access to the Meetiva website only, scoped to the team(s) they belong to.
- No panel access, no creation/invitation rights.

## Seat Limits
- Each Enterprise package purchase includes a hard cap of **20 total users**, counting Managers + Team Leaders + Members combined, **across the entire organization** — not per-project, not per-manager. The Admin (the purchaser) does **not** count toward this limit.
- **One Manager per Project** (strict — a Project cannot have two Managers), but one Manager can be assigned to multiple Projects, and different Managers on different Projects within the same org share the same 20-seat pool.
- **Worked example:** Org has 1 Manager assigned to 2 Projects, each Project has 2 Teams (4 Teams total) → 4 Team Leaders needed → that's 1 Manager + 4 Team Leaders = 5 seats used so far. The remaining 15 seats are Members, distributed across those 4 teams however the Team Leaders choose, for a total of 20. This same math applies independently if a different org instead has two separate Managers each running their own projects/teams — it's still one shared pool of 20 for the whole org.
- Enforce this at the point of credential creation (Admin creating a Manager, Manager creating a Team Leader, Team Leader creating a Member) — block creation and show a clear error once the org hits 20, regardless of which role is attempting to add the 21st user.
- **Extra seats:** once an org hits 20, adding more people requires a request up to the org's Admin, who can approve raising the seat limit. This will come with an additional per-seat fee (pricing TBD later — for now just build the request → Admin-approval → seat_limit increase pathway; leave the pricing/payment hook as a stub).
- Track remaining seats somewhere visible to the Admin (and ideally Managers, scoped to their own usage) in the Admin Panel.

## Access Matrix

| Role | Admin Panel Access | Website Access | Scope |
|---|---|---|---|
| Super Admin | Full (platform-wide) | Full | Every organization, every user, on the whole platform |
| Admin | Full (own org only) | Full | All projects/teams in own org, no other org |
| Manager | Scoped | Full | Assigned project(s)/team(s) — can span multiple projects |
| Team Leader | None | Full | Only team(s) they lead |
| Member | None | Full | Only team(s) they belong to |

## Credential Provisioning Flow
For every role below Admin, follow this pattern:
1. The higher role fills in basic info for the new user (name, email, role assignment/scope).
2. System generates login credentials (e.g. temp password or invite link with expiry).
3. Credentials are shown to the creator on-screen with a copy button — **no auto-email for now** (we're on free-tier infra and want to avoid email-sending costs/limits). The creator manually shares the credentials with the new user however they like.
4. New user logs in and should be forced to set their own password on first login.
5. Keep the email-sending step abstracted behind a single function/service so it can be swapped for auto-email later without restructuring the flow.

## Data Model Suggestions
Design (or adapt existing schema) around something like:
- `Organization` (the Enterprise tenant) — owned by one Admin (`admin_user_id`), has `seat_limit` (default 20) and `seats_used`.
- `User` — has a `role` enum (`super_admin`, `admin`, `manager`, `team_leader`, `member`). `super_admin` users have `organization_id = null` (not tied to any org); all other roles require `organization_id`. Also track `created_by_user_id`.
- `Project` — belongs to `Organization`, has exactly one `manager_id` (a Manager can have many Projects, but not the reverse).
- `Team` — belongs to a `Project`.
- `TeamLeadership` — join table linking `User` (Team Leader) to `Team`, many-to-many since one Team Leader can lead multiple teams.
- `TeamMembership` — join table linking `User` (Member) to `Team`.
- Whatever entity represents a member's work (meeting summaries, notes, uploads, etc. — use your existing content model) needs an `owner_id` pointing to `User` and should **not** cascade-delete when that user is soft-deleted. Add a lightweight status like `owner_active` / `owner_removed_pending_reassignment` so the Team Leader's UI can surface a "needs disposition" list of content left behind by removed users, and an action to reassign `owner_id` to a new user or delete the content.
- Permission checks should be enforced server-side on every request (not just hidden in the UI): `super_admin` bypasses org scoping entirely; every other role is checked against `role` + `organization_id` + assigned `project_id`(s)/`team_id`(s).

## Decisions Already Made
- A Manager **can** be assigned to multiple projects at once. A Project has **exactly one** Manager.
- A Team Leader **can** lead multiple teams (many-to-many, no extra seat cost).
- Credential handoff is **manual copy/share**, not auto-email, for now (cost reasons — build it so auto-email can be added later without a rewrite).
- **Replacement-before-removal rule:** neither a Manager nor a Team Leader can be removed until a replacement is assigned first, so the project/team is never left without one. Concretely:
  - **Team Leader removal:** the Manager picks a replacement first — either promoting an existing member of that team or assigning someone else — before the old Team Leader is removed.
  - **Manager removal:** the Admin picks a replacement first — either a specific person, an existing Team Leader being promoted, or an existing Manager who takes on this project in addition to their current one(s) — before the old Manager is removed.
- **User removal & seats:** when a user (Member, Team Leader, or Manager) is removed, their seat is freed **immediately** — no cooldown, so the Admin/Manager can add a replacement right away. Removal should be a **soft delete** (mark as `removed`, keep the record) rather than a hard delete, so history (past meetings, team membership, audit trail) is preserved without counting toward the active seat count.
- **Removed member's work stays intact and goes to the Team Leader for disposition:** if a Member is removed, none of their work (meeting summaries, notes, uploads, whatever they created/owned in that team) is deleted along with them. Instead, that content becomes visible to the Team Leader of their team, who can then choose to: reassign it to the new person filling the seat, pass it to a different existing Member, or delete it outright. Nothing should auto-delete or auto-orphan on removal — it should sit there owned-but-unassigned until the Team Leader acts on it. The same logic should apply one level up: if a Team Leader is removed, their team-level content/decisions should be handed to the incoming Team Leader (or the Manager) to review and dispose of, not deleted automatically.
- The 20-seat cap is a single shared pool for the whole org (see worked example above), with an Admin-approved "request more seats" pathway once it's hit (paid add-on, pricing TBD — stub it for now).

## Task
Implement this role system for the Enterprise package flow only, on top of the existing Meetiva frontend/backend/admin panel. Add role-based route guards / middleware enforcing the access matrix above (including the platform-wide Super Admin bypass), the seat limit logic with immediate-release soft-delete on removal, the removed-user content handoff to the Team Leader/Manager for reassignment or deletion, the manual copy/share credential flow, the replacement-before-removal rule for Managers and Team Leaders, and the Admin → Manager → Team Leader → Member provisioning chain. Keep the schema extensible so Free and Teams packages can plug in their own role logic later without a rewrite, and so auto-email can replace manual copy/share later without restructuring.
